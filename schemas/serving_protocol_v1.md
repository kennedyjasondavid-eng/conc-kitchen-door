# Inactive HOUSE serving protocol v1

The portable `HOUSE_TESTABLE_CORE serving-protocol-v1` block depends on the existing HOUSE flow-validity block and standard crypto/text APIs. It has no private-kernel dependency, network, storage, credential discovery, production caller or mode activation. The private foundation remains an independent DOOR compatibility oracle.

## Material and wire

The public material contains exactly schema, protocol, site, releaseBinding, calendar, registry, rotation, dated, datedDecisions and recipes. Release binding contains generationId and operationId; the actual private commit is attached only after private acceptance. Registry contains aggregate summary and seven headcounts. Rotation contains all84 ordered four-week services. Dated decisions and lunch/dinner replacements must agree. No resident identities, private instructions, source-file digests or evidence payloads belong in this material.

Each service has key, menu, components, unresolvedComponents, coverage, demand, sectionCounts and resolution. Complete services include componentAllocations keyed only by exact canonical recipe IDs, covering every linked component. Incomplete/unavailable services omit the entire allocation map. Manual food remains visible as an unresolved name/role/reason, without invented identity. Positive ordinary population cannot be complete with no represented food component. Recipient allocations exclude separate/anaphylactic preparation and are not summed across foods to reconcile section totals.

Recipe records distinguish source fingerprint, composite catalogue revision, unknown versus positive-only known flags and null versus explicitly verified standard-serving batch yield. Missing flags do not assert clinical negatives. Catalogue identity binds both CODEX main and shared-Library source commits plus both exact public byte hashes; a main commit alone is insufficient.

Prepare recomputes all five existing F4 component hashes, public input witness and independent public projection basis. Build attaches the exact accepted generation reference and existing allocated F4 epoch/sequence, producing exactly two files: `protocol-v1/publication.json` and `protocol-v1/releases/<epoch>/<sequence>/frame.json`. No new receipt or counter is introduced. Frame seal hashes exact canonical UTF8+LF bytes. Pointer cap is16KiB; frame cap8MiB, inclusive. Validate checks bounds, Unicode/finite JSON, canonical wire, exact pointer/frame seal, pin, F4 hashes, dates and material schema before returning the foundation projection and routing representation.

## Receiving and purpose

The API is Prepare, Build, Validate, CreateState, Begin, Promote and Resolve, with `houseServingV1` prefixes except `doorServingV1Build`. Begin and Promote return detached state values. Resolve requires an explicit purpose: headcount returns genuine section recipients; component-demand returns eligible distinct component recipients; production-scaling requires complete quantity evidence and verified canonical standard servings. Unavailable demand has `counts:null`, never a default target or fabricated zero. Verified zero remains representable.

An observed live validation failure persists a hold. A strictly valid claimed pointer may raise/conflict high-water even when its frame fails; it never admits failed content. Unsupported/malformed authority, same-occurrence conflict, newer observations and stale attempts cannot be healed by old cache. Cache reads preserve the original live age. Valid restored data needs actual validation/promotion before operational use; invalid restoration stays quarantined until a valid live observation. Historical display and operational eligibility remain separate.

A failed public pointer/frame/pointer read may retain an exact bounded observation with pointer and optional previousPointer. Both members must independently pass the strict pointer schema before either affects authority; they are observed previous→current. An invalid pair contributes no pointer authority and still leaves the ordinary live hold. This preserves an observed newer pointer or same-occurrence conflict across a changed reread without admitting any failed frame.

Because state is functional, the real receiving owner MUST compare the operation's attempt against its CURRENT owner generation after every await and before installing state, caching, changing menus/counts/holds or producing side effects. The pure API cannot observe another invocation's replacement state. Real owner overlap tests are required; passing pure stale-token tests alone does not prove concurrent loader safety.

## Activation boundary

Hashes certify integrity of the supplied frame, not source authentication, clinical suitability, actual Git commitment, delivery or receiving-device adoption. Actual byte/provenance catalogue verification, independent private derivation, source-leased occupant episodes and instructions, preparation/containment, native publication and recovery, paired six-app loaders/cache/compute/export tests and staff/Office acceptance remain required. Public consumers can certify only the released frame as of its observation. DOOR's final serving action must separately check current private accepted authority against the released pin.

No pointer presence, successful synthetic test or installed shared block switches a device into protocol mode. Explicit shared site capability, paired deployment/reload and observed intended-device cutover remain separate work. Existing operational data and active serving behavior are unchanged by this module.
