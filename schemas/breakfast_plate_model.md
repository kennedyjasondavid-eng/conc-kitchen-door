# Breakfast resolved-plate model — inactive foundation, revision 0

This document owns the proposed internal breakfast model. **Revision 0 is an in-memory function interface, not an activated menu, registry or published-feed schema.** Nothing reads/writes this model in current service flows. Existing contracts and app stamps are unchanged. The [action plan](../docs/DOOR_PLATING_RECONCILIATION_ACTION_PLAN_2026-11-16.md) owns execution state; the [B0 evidence](../docs/DOOR_BREAKFAST_MATRIX_AND_REPRESENTATION_2026-11-16.md) owns the manual comparison and combined-requirement failures.

## Inputs and ownership

`doorResolveBreakfastPlate(request, variants, catalogue, preferredVariantId = null)` is synchronous and pure. Inputs are explicit snapshots. No localStorage, live fetch, room-list matching, global routing priority, UI state or clock is read. All returned data is detached. Strings identify exact keys; no name-based ingredient inference or fuzzy recipe matching is allowed. Lexical sorting makes candidate order irrelevant.

| Input | Required fields | Meaning |
| --- | --- | --- |
| Request | `service`, `residentKey`, `anaphylacticDisposition`, `requirementSource`, `requirements` | One resident/service, supplied by a future private adapter |
| Requirement source | `complete: true`, `revision` | Adapter attests that all applicable current restrictions, exclusions, accommodations, specified components and preparation/portion requests are included. A deliberate empty list differs from missing/incomplete input. The function cannot infer omitted facts. |
| Requirement | `id`, `revision`, `kind`, optional `role` | Independent predicate; `kind` is `ingredient`, `component`, `preparation` or `portion`. Ingredient predicates apply to every component. Component predicates apply to every component with the specified exact role; a missing role remains unresolved. |
| Variant | `id`, `service`, `state`, `components`, `preparation`, `sources`, `assessments` | A complete assembly. State is `standard-suitable`, `replacement` or `unresolved`; the last is never eligible. State alone supplies no compatibility proof. |
| Component | `id`, `role`, `recipeId`, `name`, `fingerprint`, `portion` | Exact canonical recipe/product reference. Component IDs are unique within a plate. `portion` is explicitly `null` when unknown, or `{amount: positive finite number, unit: nonempty string}`. No implicit one-portion default. |
| Catalogue | `revision`, `recipes` | Adapter-provided, verified canonical CODEX snapshot plus assessments derived from its facts. This is a function input, not a second recipe database. Recipe IDs are unique. |
| Catalogue recipe | `recipeId`, `name`, `fingerprint`, `sources`, `requirements` | Component name and fingerprint must match exactly. A recipe's `requirements` map holds independent ingredient/component predicate assessments. |
| Recipe assessment | `requirementRevision`, `status`, `sources` | Status `covered`, `conflict` or `unknown`, bound to this recipe fingerprint and exact requirement revision. Nonempty evidence references are mandatory. Unmapped or missing facts remain unknown; no plate assertion can override recipe conflicts. |
| Plate assessment | `requirementId`, `requirementRevision`, `status`, `sources`, `basis` | Only preparation/portion predicates belong here. `basis` is the exact `doorBreakfastVariantBasis(variant)` token over its component array and preparation instructions. Edits invalidate the evidence. Extra/duplicate or ingredient assertions are rejected. The adapter projects only the request's applicable preparation/portion assessments. |

`sources` is an array of nonempty evidence reference strings. Revision 0 checks structure and bindings; a reference string is not itself verified evidence. The future adapter must authenticate canonical provenance, interpret CODEX's supported facts, reject unknown facts, and construct meaningful requirement predicates. The current raw CODEX catalogue does **not** natively contain this `requirements` map. This model does not add assessments to CODEX or claim that today's ingredient data proves a commercial product suitable.

The model keeps GF, vegetarian, No Eggs, No Dairy, lactose intolerance, halal, specified milk, texture/preparation and portions independent. For instance, the oat-milk predicate applies to the milk role, while GF and No Dairy apply to the entire assembly. A group heading cannot cover those predicates. Missing evidence for any applicable accompaniment blocks that variant.

The future adapter must derive `anaphylacticDisposition` from the existing conflict and roommate containment engine, before ordinary plate resolution. `separate` returns a separate disposition without selecting a plate. `standard-pool` is explicit, not a default or a generic “handled” waiver. This function never clears anaphylactic flags, acknowledges service or approves an anaphylactic alternative.

## Resolution and quantities

All required predicates must be covered by current evidence. Conflicts and unknowns prevent selection. One eligible variant resolves the definition; multiple eligible variants are ambiguous. An explicit preferred ID is accepted only if that variant is currently eligible. Unknown/missing preferences cannot fall back to another plate. Rejected candidate IDs and reasons are returned in stable order.

`resolved` means the supplied definition meets the supplied request and evidence under this interface; it does not certify omitted requirements, physical preparation, clinical texture, products or service. `unresolved` provides no selected components. Malformed/duplicate requirement, recipe, variant, component or assessment identities fail closed.

A qualitative instruction such as “smaller starch portion plus extra protein” can be retained and evidenced as qualitative, without inventing grams or pieces. If a numerical quantity or preparation detail is itself required and unknown, that predicate remains unknown and the plate does not resolve. A resolved definition with unspecified non-required quantities still has incomplete quantitative totals.

`doorAggregateBreakfastPlates(assignments, expectedResidentKeys)` requires exact, unique full-roster coverage of one service, including unresolved and separated residents. An incomplete/mixed/duplicate roster fails. It aggregates only resolved components and lists unresolved and separately handled residents explicitly. `complete` concerns ordinary-pool assignment coverage; `quantitiesComplete` is separate. Anaphylactic/roommate components stay excluded under the existing policy and must not be represented as zero required food.

Each component occurrence contributes one allocation. Intentional repeated occurrences use distinct component IDs; duplicate IDs are invalid. Totals retain exact recipe identity/fingerprint, role, per-serving quantity/unit and preparation array. Different recipes, revisions, quantities, units or materially different preparation remain separate groups. No unit conversion is inferred. Unknown portions retain `quantityTotal: null`; unresolved residents contribute no fabricated food quantities. Total allocations and distinct recipient identities are both retained. Results describe only the supplied complete roster, never an independently inferred population.

A component may reference a complete canonical assembly or an individual dish. The future authoring adapter must choose one representation consistently: it must not include both an assembly and its constituent sides. There is no automatic splitting, recipe expansion or side-appending in this resolver.
