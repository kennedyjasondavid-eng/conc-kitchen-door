# F6 delivery and unchanged-save contract draft

This is an implementation proposal for the approved F6 slice, awaiting independent contract review and frozen actual-publisher gates. It does not activate a feature. F1 owns atomic publishing; F4 owns coherent content and publication occurrences. Reuse both mechanisms and the existing outbox.

## Two independent decisions

Before allocating another occurrence or writing Git objects, compare the complete desired staged operation with the coherent, pinned authoritative committed operation. Ignore only explicitly identified export/check timestamps and the newly proposed occurrence. Preserve meaningful menu, calendar, recipe, registry, anaphylactic, operator-rule, removal, special, and staff-record changes. A private publication counter ahead of the public artifacts is a repair requirement, even when logical content matches an older occurrence. A matching digest alone cannot waive structural validation or missing artifacts.

An unchanged operation produces no content commit. Whether Pages is delayed, failed, stale, inaccessible, or already served does not change that decision. A changed operation produces one atomic commit after CAS validation, with the existing conflict/recovery behavior. Do not clear local edits made after the captured operation. An urgent edit uses the existing prompt flush; do not introduce a timer that delays every save. Existing outbox logical boundaries should coalesce equivalent work before considering any additional debounce.

## Durable delivery state

Keep one minimal local receipt beside the existing transaction/outbox state. Record site/repository, committed Git revision, validated F4 content receipt, commit observation time, served evidence, and consumed evidence separately. The receipt contains no token or resident detail. Local pending intent remains owned by its current operation and is never inferred from the latest delivery receipt.

Committed means the atomic ref update landed or was recovered by pinned proof. Served means anonymous public reads verify the expected coherent public set, or a genuinely later coherent publication that safely supersedes it. Consumed means EXPO has actually accepted that occurrence; a closed EXPO is simply unobserved. Reuse F4's existing `_doorMenu.flow` aggregate in EXPO's HUB schedule publication, emitted only when the schedule was built from a complete accepted flow; do not add a competing `_doorFlow` field. A network response, schema version, generated timestamp, or matching menu wording is insufficient evidence. A newer routing receipt alone does not prove that EXPO scheduled it.

Healthy progression stays quiet. While delivery is outstanding, staff-facing wording distinguishes saved on this computer, committed with delivery pending, and verified available to the kitchen. Never report "sent to the kitchen" solely from Git success. Unobserved EXPO consumption does not by itself alarm or trigger another write.

## Bounded verification and recovery

Reuse boot/focus/manual-save refresh opportunities. A new committed revision gets a small bounded verification attempt sequence, with cache-busted no-store reads. A failed attempt retains the same debt and original commit; restart restores it without extending any evidence age. Stop when verified, genuinely superseded, or the bounded attempt budget is exhausted. Do not add an Actions cron, a background service, or persistent rapid polling.

If delivery is still pending, inspect the existing Pages run when the configured authorization allows it. Retry that existing failed deployment only through a supported, bounded authorized action. If retry permission or a suitable run is unavailable, retain an actionable pending status for that revision and link to the existing deployment surface. Do not manufacture a content commit as a deployment retry. No new credential permissions are assumed.

## Frozen acceptance required before build

Use the real publisher with intercepted Git and Pages responses. First prove a changed operation lands, then repeat unchanged saves while Pages remains stale or failed: zero extra content commits, debt survives, and no premature served/consumed claim. A second device starts without the first device's local receipt and must also deduplicate against pinned authoritative content. Cover initial legacy/unactivated F4 behavior explicitly; do not compare absent receipts as if equal certified content.

Cover lost Git acknowledgement, close/reopen, later Pages recovery, unavailable deployment-retry permission, EXPO closed, a genuinely superseding publication, newer local edits during verification, a roster-only change, recipe rebind, dated scope change, real revert, private-counter repair, and non-identical staff records. Different prep/cook/send representations do not create new logical DOOR saves. Existing F1 recovery and F4 occurrence/coherence gates remain unchanged and passing.

The reviewers must settle the exact receipt shape, finite attempt schedule, public serving proof, and additive EXPO consumption signal before the gate author freezes interfaces. A pure helper passing does not replace actual publisher/UI verification. Deployment retry and served/consumed claims must be backed by observed capability, not inferred from a successful Git write.

## Review decisions for the frozen interface

The release reviewer found that F4's `_doorMenu.flow` can survive an EXPO workbook import in older code. That field alone cannot certify consumption or downstream quantity authority. Root moved the minimal completed-build capability into F4; reuse its `_doorMenu.buildAttestation:{schema:1,capability:'door-flow-build-v1',inputRevision,publication}` and the existing aggregate flow. The F4 completed-build authority section owns emission, effective-input checks and paired mixed-version acceptance. It binds the completed build, not the most recent fetch, and does not equate unrelated DOOR/EXPO recipe-feed digests. DOOR requires this exact capability and full receipt agreement before marking consumption observed. Older publishers, missing attestation, imported/manual sources and stale completed builds remain unobserved. Registry-only replacement can certify a rebuilt compatible schedule; a new routing receipt alone cannot. The attestation repeats only the minimal occurrence/input key, not the whole flow record.

Store delivery receipts under the existing local storage discipline as scope-keyed records. Each record is `{schema:1,repo,branch:'main',site,operationId,committedSha,committedAt,flow,publicDigests,served,consumed,attemptCount,lastAttemptAt,nextDueAt,retryRunId}`. `flow` is the aggregate receipt or null; `publicDigests` contains canonical SHA256 digests of exactly the seven public JSON artifacts read at the pinned committed head, never private content. `served` and `consumed` are independently nullable `{observedAt,publication,inputRevision}` evidence; legacy served evidence uses `{observedAt,committedSha}` and cannot authorize consumed evidence. Retain an unresolved record when changing repository/site; a different scope is neither proof of delivery nor permission to clear it. Never store tokens or resident detail in these records.

One committed revision receives at most three automatic verification attempts, due at 0, 5 and 30 seconds after its original `committedAt`. Persist the attempt count before each request. Restart, focus and unchanged saves resume only a due unused attempt; they do not renew the budget or original timestamps. An explicit delivery recheck permits one additional read attempt without a content commit. Each request has an eight-second timeout; coalesce concurrent triggers by scope/revision. Expired evidence is displayed as historical rather than refreshed by touching storage. No continuous polling follows exhaustion. After a served proof, one still-unused budgeted attempt may observe EXPO consumption; unobserved consumption alone stays quiet.

For flow-bearing delivery, use the reviewed F4 seven-file validator and exact occurrence/input equality for serving proof. A later, internally coherent receipt may supersede debt only within the same repository, site, branch and epoch and with a strictly higher sequence; different epochs/content hashes are not orderable. Record that later occurrence explicitly. For legacy/unactivated delivery, require all seven pinned public digests to match the anonymous read as a complete set; two absent flow receipts never imply equality. Legacy serving proof remains explicitly uncertified for routing/consumption. An unreadable supporting file leaves debt pending.

Unchanged detection compares every staged artifact against that same immutable head before allocating a new occurrence or creating Git objects. Missing artifacts, malformed bodies, a private counter requiring repair, meaningful metadata, staff records, anaphylactic changes and removal history cannot be omitted. The only ignored values are `_meta.exported`, `_meta.builtFromMenu.exported` and a validated proposed flow publication occurrence; field names elsewhere remain significant. Preserve array order unless an existing reviewed contract defines it as a set. A second device uses the same pinned content proof without relying on another device's local receipt. Prepared recovery retains its stronger exact landed-occurrence proof.

Deployment recovery initially supplies a link to the existing Actions deployment surface for the recorded repository/revision. Automatic rerun is not part of this implementation: no verified existing credential capability authorizes that extra action. Retain `retryRunId:null` as an explicit inactive field, and do not request broader permissions. This meets the pending-delivery fallback without generating a content commit or extra scheduled run. A later rerun capability would need its own reviewed bounded action.

Freeze actual publisher tests for this interface, including the old-producer/imported/manual/stale-build consumption negatives and the rebuilt/registry-only positives. These decisions are ready for independent closure review before the gate author starts implementation acceptance.

### Evidence age and successive commits

Use F4's seven-day bound for current delivery wording: `0 <= now - observedAt <= 7 * 86400000`. Missing, malformed, future-dated or older evidence cannot support a current verification claim. Retain it as historical evidence with its original observation time; reading/touching storage, focusing the tab and exhausting/restarting verification never renew that time. An actual successful new verification read may record a new observation, but a CDN contact or failed/partial response cannot. Expired evidence exposes the existing explicit recheck action without creating a new publish, resetting the automatic attempt budget or claiming delivery has failed.

Consumption means only that EXPO accepted that publication in a completed build. Even within seven days, it is not proof that today's schedule was rebuilt or that a passed dated service remains current; F4's service-date and source validity continue to govern those claims. Older consumption is labelled as a past acceptance, never current production scheduling.

Keep one latest committed operation per repository/branch/site scope, not a growing per-save queue. A newer complete atomic committed operation may replace that scope's earlier receipt because it represents the new authoritative desired state. Its receipt begins pending, with its own immutable commit identity/time and fresh three-attempt budget; it inherits no served/consumed credit from the earlier operation. This replacement does not erase pending delivery: only exact or genuinely later coherent public proof clears it. An unchanged save is not a new operation and cannot replace/reset the receipt. Different scopes remain separate, and local intent newer than either committed operation stays owned by the existing outbox.
